TALLER 7.2 · EN TU COMPUTADOR

Dos microservicios conectados y protegidos con un circuit breaker

Vas a crear desde cero el servicio de inventario y el de pedidos, unirlos por HTTP, ver cómo uno tumba al otro y arreglarlo. Cada paso termina con algo que ejecutas y compruebas.

Paso 0. Prepara tu máquina

Necesitas JDK 21, un editor (IntelliJ IDEA Community o VS Code) y curl, que ya viene en Windows 10/11, macOS y Linux. No necesitas instalar Maven: cada proyecto trae su propio Maven Wrapper (mvnw).

$ java -version
# debe empezar por: openjdk version "21...
$ curl --version
# cualquier versión sirve

Crea una carpeta vacía tienda-aurora. Ahí vivirán los dos servicios, uno al lado del otro.

Paso 1. Crea el proyecto de inventario

Entra en start.spring.io, el generador oficial de proyectos Spring Boot, y rellena así:

Pulsa Generate, descomprime el zip dentro de tienda-aurora y ábrelo en el editor. La estructura que te interesa:

inventario/
├── mvnw, mvnw.cmd          ← Maven Wrapper
├── pom.xml                 ← dependencias y versión de Java
└── src/
    ├── main/java/com/aurora/inventario/
    │   └── InventarioApplication.java   ← ya viene hecho
    ├── main/resources/application.properties
    └── test/java/com/aurora/inventario/
Qué es cada cosa
pom.xml es el archivo de Maven: dice qué librerías usa el proyecto. InventarioApplication tiene el main que arranca un servidor web embebido (Tomcat). No tienes que instalar ningún servidor aparte.

Paso 3. Arráncalo y pruébalo

Abre una terminal en la carpeta inventario. En Windows usa mvnw.cmd en lugar de ./mvnw. La primera vez tarda unos minutos porque descarga las librerías.

$ ./mvnw spring-boot:run
...
Tomcat started on port 8081 (http) with context path '/'
Started InventarioApplication in 5.378 seconds

Deja esa terminal abierta y, en otra, llama al endpoint:

$ curl localhost:8081/stock/TEC-1042
{"sku":"TEC-1042","unidades":15}
Punto de control. si ves ese JSON, tu primer microservicio funciona. Prueba también curl -i localhost:8081/stock/XXX-0000: la primera línea debe decir 404.

Paso 4. Protégelo con una prueba automática

Una prueba deja escrito lo que el servicio debe hacer, para que un cambio futuro no lo rompa sin que te enteres. @WebMvcTest levanta solo la capa web y MockMvc simula las peticiones sin abrir un puerto real.

$ ./mvnw test
...
Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS

Paso 5. Crea el proyecto de pedidos

Vuelve a start.spring.io con los mismos valores, pero Artifact pedidos y dos dependencias: Spring Web y Spring Boot Actuator. Descomprímelo también dentro de tienda-aurora. Ahora tienes dos proyectos hermanos: dos programas independientes que se compilan y arrancan por separado.

tienda-aurora/
├── inventario/   ← puerto 8081
└── pedidos/      ← puerto 8080

Paso 6. Une pedidos con inventario

Los microservicios se hablan por HTTP, igual que tu curl. Pedidos necesita tres piezas: el tipo de dato que devuelve, un cliente que llama a inventario y un endpoint propio.

ElementoQué hace
RestClientEl cliente HTTP de Spring. Hace la petición y convierte el JSON de respuesta en un objeto Java.
@Value("${inventario.url}")Lee la dirección de inventario de la configuración. Es la unión entre los servicios: si mañana inventario cambia de máquina, solo cambias este valor.
setConnectTimeout / setReadTimeoutTiempo máximo para conectar (1 s) y para recibir la respuesta (2 s). Sin ellos, una llamada lenta podría esperar indefinidamente.
RespuestaInventarioCopia la forma del JSON de inventario. Pedidos no comparte código con inventario: solo conoce su contrato HTTP.

Borra application.properties de pedidos y crea en su lugar application.yml:

${INVENTARIO_URL:http://localhost:8081} significa: usa la variable de entorno INVENTARIO_URL si existe; si no, localhost:8081. En tu PC vale el valor por defecto; en Docker (sección 7.3) se cambia sin tocar el código.

Paso 7. Prueba la unión

Necesitas dos terminales abiertas a la vez, una por servicio:

# terminal 1, en inventario/
$ ./mvnw spring-boot:run

# terminal 2, en pedidos/
$ ./mvnw spring-boot:run
Tomcat started on port 8080 (http) with context path '/'

Y en una tercera, llama a pedidos. Pedidos, a su vez, llama a inventario:

$ curl localhost:8080/pedidos/stock/TEC-1042
{"sku":"TEC-1042","unidades":15,"origen":"inventario"}
Punto de control. "origen":"inventario" confirma que la respuesta viajó por los dos servicios.

Paso 8. Rómpelo: apaga inventario

Ve a la terminal 1 y detén inventario con Ctrl+C. Repite la llamada:

$ curl localhost:8080/pedidos/stock/TEC-1042
{"timestamp":"2026-11-24T20:31:30.346+00:00","status":500,"error":"Internal Server Error","path":"/pedidos/stock/TEC-1042"}

Y en la terminal 2, el log de pedidos muestra la causa:

ResourceAccessException: I/O error on GET request for "http://localhost:8081/stock/TEC-1042": Connection refused (connect failed)

Pedidos estaba sano, pero respondió 500 porque dependía de inventario. Aquí inventario está apagado y el fallo es instantáneo. Si en vez de apagado estuviera lento, cada petición quedaría esperando hasta el timeout y los hilos de pedidos se agotarían. Así un servicio tumba a otro: es la falla en cascada.

Paso 9. Añade el circuit breaker

Un circuit breaker lleva la cuenta de las últimas llamadas. Si demasiadas fallan, se abre y deja de llamar a inventario durante un tiempo: responde al instante con un respaldo. Pasado ese tiempo pasa a semiabierto y deja pasar unas pocas llamadas de prueba; si salen bien, se cierra otra vez.

PropiedadSignificado
sliding-window-size: 10Recuerda las últimas 10 llamadas.
minimum-number-of-calls: 5No decide nada hasta tener al menos 5.
failure-rate-threshold: 50Se abre si el 50 % o más de la ventana falló.
wait-duration-in-open-state: 10sTiempo que permanece abierto antes de probar de nuevo.
permitted-number-of-calls-in-half-open-state: 3Llamadas de prueba en semiabierto.
include: health,circuitbreakersPublica el estado del breaker en /actuator/circuitbreakers para que puedas verlo.

Paso 10. Repite el experimento

Reinicia pedidos (Ctrl+C y otra vez ./mvnw spring-boot:run) con inventario encendido, y haz 5 llamadas normales. Luego apaga inventario y llama 7 veces más. Esta es la salida real; el tiempo entre paréntesis lo añade curl -w ' (%{time_total} s)':

$ curl localhost:8080/pedidos/stock/TEC-1042   # intento 1
{"sku":"TEC-1042","unidades":null,"origen":"respaldo"}   (0.008165 s)
$ curl localhost:8080/pedidos/stock/TEC-1042   # intento 2
{"sku":"TEC-1042","unidades":null,"origen":"respaldo"}   (0.003957 s)
...
$ curl localhost:8080/pedidos/stock/TEC-1042   # intento 7
{"sku":"TEC-1042","unidades":null,"origen":"respaldo"}   (0.003036 s)

$ curl localhost:8080/actuator/circuitbreakers
{"circuitBreakers":{"inventario":{"failureRate":"50.0%", ... ,"bufferedCalls":10,
  "failedCalls":5, ... ,"notPermittedCalls":2,"state":"OPEN"}}}

Lee el JSON con calma, porque cuenta la historia completa. La ventana tiene 10 llamadas: las 5 buenas del principio y 5 fallidas. Con la quinta falla la tasa llegó al 50 % y el breaker se abrió (OPEN). Los intentos 6 y 7 ya no salieron hacia inventario: son los 2 notPermittedCalls. Ya no hay error 500: pedidos responde siempre, y deja claro con "origen":"respaldo" que el dato no es fiable.

Ahora enciende inventario, espera más de 10 segundos y llama 4 veces mirando el estado después de cada llamada:

intento 1 → {"sku":"TEC-1042","unidades":15,"origen":"inventario"}   estado: HALF_OPEN
intento 2 → {"sku":"TEC-1042","unidades":15,"origen":"inventario"}   estado: HALF_OPEN
intento 3 → {"sku":"TEC-1042","unidades":15,"origen":"inventario"}   estado: CLOSED
intento 4 → {"sku":"TEC-1042","unidades":15,"origen":"inventario"}   estado: CLOSED
Punto de control. las 3 llamadas de prueba salieron bien, así que el breaker volvió a CLOSED solo, sin reiniciar nada.
Advertencia
El respaldo devuelve unidades: null, que significa «no sé», y no 0. Un respaldo que inventa datos es peor que un error: con 0 cancelarías ventas que sí podían hacerse.

Paso 11. Prueba automática del breaker

Lo que acabas de comprobar a mano queda fijado en una prueba. La propiedad apunta inventario a un puerto donde no hay nadie, así que todas las llamadas fallan:

$ ./mvnw test
...
Tests run: 2, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS

Si algo falla

Mensaje o síntomaTipoQué revisar
Web server failed to start. Port 8080 was already in use.EntornoOtro programa (o una ejecución anterior que no cerraste) ocupa el puerto. Ciérralo, o busca cuál es: Apéndice A.
Pedidos responde 500 aunque inventario está encendidoTemaMira el log de pedidos. Si dice Connection refused, revisa inventario.url y que inventario esté en el 8081.
El breaker nunca se abreTema¿Hiciste al menos 5 llamadas? ¿Añadiste spring-boot-starter-aop? Sin AOP la anotación se ignora sin avisar.
release version 21 not supportedEntornoEstás compilando con un JDK anterior al 21. Revisa java -version (Paso 0).
