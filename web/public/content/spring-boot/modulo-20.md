# Módulo 20: Proyecto integrador: backend de entregas productivo


## Aprende construyendo

Los Temas 1–3 amplían incrementalmente el proyecto real `examples/spring-boot-integrador-rutaflow/`, combinando piezas ya estudiadas en el track: entidades y migraciones Flyway (Módulo 4), JWT y `@PreAuthorize` (Módulo 5), pruebas de integración con Testcontainers (Módulo 6) y una métrica de negocio de Actuator (Módulo 7). Cada tema comprueba cambios con código ejecutable y evidencia observable. Los Temas 4–9 construyen el backend de entregas `gestion-entregas`: datos espaciales en MySQL, JWT con propiedad del recurso, tiempo real con STOMP y archivos con notificaciones.

### Tema 1: Arquitectura del microservicio integrador · Avanzado · 40 min

**Resultado del tema:** construirás y comprobarás un endpoint que valida una solicitud, pasa por controller → service → repository y guarda una entrega en PostgreSQL. Al final podrás explicar qué hace cada capa con evidencia de una petición HTTP y una fila guardada.

**¿Por qué es importante?** Separar HTTP, reglas del servicio y persistencia hace que cada cambio tenga un lugar claro. La prueba de extremo a extremo comprueba que esas piezas sí trabajan juntas.

**Necesitas:** Java 25, Maven Wrapper y Podman o Docker compatible con Testcontainers. Abre [`examples/spring-boot-integrador-rutaflow/`](https://github.com/NICORUIZ93/The_Imperial_Book/tree/main/examples/spring-boot-integrador-rutaflow). La práctica ya contiene el proyecto ejecutable; los subtemas indican qué archivo seguir, qué cambiar y cómo comprobarlo.

#### Subtema 1.1: Sigue una petición por las capas · 8 min

**1. Contexto**

Una petición no debería decidir cómo se guarda en la base de datos. El controller entiende HTTP; el service aplica la acción del producto; el repository habla con PostgreSQL.

**2. Hazlo tú**

Abre `src/main/java/academia/rutaflow/integrador/entrega/` y sigue `EntregaController.java` → `EntregaService.java` → `EntregaRepository.java`. Desde `examples/spring-boot-integrador-rutaflow/` ejecuta:

```bash
./scripts/verify-integration.sh
```

```text
POST /api/entregas
  JSON → EntregaController → EntregaService → EntregaRepository → PostgreSQL
  HTTP 201 ← EntregaResponse ← entidad guardada
```

**Resultado esperado:** la suite final informa 7 pruebas y 0 fallos; la petición de creación devuelve HTTP 201 y una URL `Location`.

**Fallo deliberado:** cambia temporalmente `@PostMapping` por `@PutMapping` y ejecuta `./scripts/verify-integration.sh`. **Diagnóstico:** la prueba recibe un estado distinto a 201 porque envía POST. Restaura `@PostMapping`.

**3. Entiende**

El flujo se puede seguir leyendo los archivos: el controller convierte la entrada y la respuesta HTTP, el service coordina la operación y el repository persiste. El diagrama recorta las capas de datos; el laboratorio final ya incluye JWT y métricas, que se analizan en el Tema 2. No incluye entrega de eventos a un broker.

**4. Cierra**

Sin mirar los archivos, explica qué clase recibe HTTP y cuál guarda los datos. Luego señala la línea de código que conecta cada paso.

#### Subtema 1.2: Deja que Flyway cree la tabla · 10 min

**1. Contexto**

La entidad Java describe los datos que usa la app. La migración SQL define el cambio que se aplica a la base. Así, el esquema no depende de que Hibernate invente tablas al arrancar.

**2. Hazlo tú**

Compara `src/main/resources/db/migration/V1__crear_entrega.sql` con `entrega/Entrega.java`. Ejecuta `./scripts/verify-integration.sh`.

```sql
CREATE TABLE entrega (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    destinatario VARCHAR(200) NOT NULL,
    estado VARCHAR(30) NOT NULL
);
```

En `application.properties`, `spring.jpa.hibernate.ddl-auto=validate` pide comprobar que la tabla coincide; Flyway aplica la migración.

**Resultado esperado:** Flyway aplica la migración y Hibernate valida la tabla antes de ejecutar las siete pruebas.

**Fallo deliberado:** renombra la migración para que ya no empiece con `V1__` y vuelve a ejecutar `./scripts/verify-integration.sh`. **Diagnóstico:** Flyway no la reconoce y la validación de Hibernate falla porque falta `entrega`. Restaura el nombre `V1__crear_entrega.sql`.

**3. Entiende**

La migración deja un historial de cambios del esquema. La entidad y el SQL deben coincidir: por ejemplo, ambos limitan `destinatario` a 200 caracteres.

**4. Cierra**

Di qué archivo define la tabla y qué propiedad evita que Hibernate la cree por su cuenta.

### Tema 2: Integra seguridad JWT y observabilidad · Avanzado · 40 min

**¿Por qué es importante?** La base de datos no sabe quién hizo una solicitud y un contador no prueba que el trabajo terminó. El servicio valida identidad y permiso antes de escribir, y registra la métrica después de guardar.

#### Subtema 2.1: Verifica un JWT firmado · 10 min

**1. Contexto**

Un JWT es una credencial firmada. La API valida la firma y la caducidad antes de confiar en sus datos; cambiar texto del token no crea una identidad válida.

**2. Hazlo tú**

Abre `src/main/java/academia/rutaflow/integrador/security/JwtSecurityConfig.java`. Sigue el bean `jwtDecoder`, que valida HS256 con una clave, y `jwtAuthenticationConverter`, que lee el claim `roles`. En `src/test/java/academia/rutaflow/integrador/entrega/ArquitecturaIntegradaTest.java`, busca `token(...)`: crea una credencial firmada para las pruebas. Ejecuta:

```bash
./scripts/verify-integration.sh
```

**Resultado esperado:** la app inicia y las siete pruebas pasan; los requests de creación llevan `Authorization: Bearer ...`.

**Fallo deliberado:** cambia en el convertidor el claim `roles` por `perfiles` y ejecuta el script. **Diagnóstico:** el token todavía tiene una firma válida, pero el convertidor ya no encuentra la autoridad y el request con `ROLE_USER` recibe 403. Restaura `roles`.

**3. Entiende**

`JwtDecoder` verifica la credencial; el convertidor transforma el claim de roles en autoridades de Spring Security. La API consume tokens, no ofrece un endpoint para emitirlos. El valor por defecto solo sirve en local; para ejecutar con tu propia clave define `RUTAFLOW_JWT_SECRET_BASE64`. En producción, conecta un emisor de identidad y guarda las claves fuera del repositorio.

**4. Cierra**

Explica qué revisa la firma y de qué claim sale `ROLE_USER`. Señala por qué el token de la prueba es distinto de escribir un nombre en un encabezado.

#### Subtema 2.2: Distingue identidad de permiso · 10 min

**1. Contexto**

Tener un token válido confirma quién hace la llamada; no significa que esa persona pueda crear cualquier recurso. El endpoint exige el rol `USER`.

**2. Hazlo tú**

En `entrega/EntregaController.java`, localiza `@PreAuthorize("hasRole('USER')")`. En `ArquitecturaIntegradaTest.java`, corre el caso `escrituraRequiereJwtValidoYRolUser`: sin token espera 401; con token válido de `ROLE_ADMIN` espera 403.

```bash
./scripts/verify-integration.sh
```

**Resultado esperado:** 401 sin token o con firma alterada; 403 si el token es válido, pero no tiene el rol requerido.

**Fallo deliberado:** quita `@PreAuthorize` y ejecuta el script. **Diagnóstico:** el token `ROLE_ADMIN` alcanza el endpoint y devuelve 201; `anyRequest().authenticated()` valida identidad, pero no el rol de negocio. Restaura `@PreAuthorize`.

**3. Entiende**

`@EnableMethodSecurity` activa la regla sobre el método. La cadena HTTP exige autenticación general, usa sesiones sin estado y `@PreAuthorize` aplica el permiso concreto de esta acción. No uses un test con usuario simulado para afirmar que la firma JWT se verificó: aquí el test firma un token y altera otro para confirmar que el filtro rechaza la firma rota.

**4. Cierra**

Di qué respuesta esperas para (a) sin credencial, (b) firma alterada, (c) token válido con rol incorrecto y (d) token válido con `ROLE_USER`. Relaciona cada caso con la regla que lo produce.

#### Subtema 2.3: Cuenta solo las entregas guardadas · 10 min

**1. Contexto**

El contador debe representar trabajo terminado. Si sumas antes de guardar, puede informar una entrega que la base rechazó.

**2. Hazlo tú**

Abre `entrega/EntregaService.java`. Localiza el orden: `entregas.save(...)` y luego `entregasCreadas.increment()`. En la prueba `jwtConRolUserCreaYActuatorMuestraElContador`, compara el contador antes y después de una creación.

```java

entregasCreadas.increment();
```

Ejecuta `./scripts/verify-integration.sh`.

**Resultado esperado:** la prueba observa que el contador sube exactamente en 1 tras la respuesta 201.

**Fallo deliberado:** comenta `entregasCreadas.increment()` y ejecuta el script. **Diagnóstico:** PostgreSQL guarda la entrega y el endpoint responde 201, pero la aserción del contador no aumenta. Restaura la línea.

**3. Entiende**

### Tema 4: CRUD API y contratos · Intermedio · 35 min

**¿Por qué es importante?** Cancelar sin borrar conserva evidencia útil para auditoría y evita que un reintento de red destruya información o cree un resultado distinto. En este laboratorio, `DELETE` marca el envío como cancelado; no borra la fila. Las claves para reintentar una creación se estudian en M17 T2.

#### Subtema 4.1: Modela estados que sí existen · 8 min

**Contexto:** Una cadena libre como `"cancelado"` puede terminar con errores de escritura y estados inventados.

**Hazlo tú:** Abre `examples/spring-boot-cancel-rutaflow/src/main/java/academia/rutaflow/cancel/entrega/EstadoEnvio.java` y `Envio.java`. Sigue el valor inicial y el método `cancelar()`.

```java
public enum EstadoEnvio { CREADO, CANCELADO }

public void cancelar() {
    this.estado = EstadoEnvio.CANCELADO;
}
```

Ejecuta el test que crea y lee un envío desde `examples/spring-boot-cancel-rutaflow/`:

```bash
./mvnw -q test -Dtest=CancelacionContratoTest#crearPublicaLocationYGetRecuperaElDto
```

**Recorrido del mensaje:** la app se conecta a `/ws-entregas`; el servidor publica en `/topic/entregas/SHP-1`; el cliente suscrito a ese destino recibe el JSON. Piensa en el topic como un canal de radio: escuchar el canal de otro envío no recibe esta posición.

El laboratorio autocontenido está en `examples/spring-boot-stomp-rutaflow/`. Abre terminal en esa carpeta y ejecuta `./mvnw -q test`. Usa servidor embebido, puerto aleatorio, un cliente `WebSocketStompClient` real y un broker simple local.

```bash
cd examples/spring-boot-stomp-rutaflow
./mvnw -q test
```

#### Subtema 8.1: Abre la conexión y define destinos · 8 min

**Contexto:** El endpoint es la puerta de entrada WebSocket. `/app` señala mensajes que el servidor procesa y `/topic` señala canales de publicación.

**Hazlo tú:** Abre `examples/spring-boot-stomp-rutaflow/src/main/java/academia/rutaflow/stomp/StompConfig.java`. Lee las tres líneas que definen los destinos:

```java
registry.enableSimpleBroker("/topic");
registry.setApplicationDestinationPrefixes("/app");
registry.addEndpoint("/ws-entregas");
```

En `StompEndToEndTest.java`, localiza la conexión `ws://localhost:` y compárala con `/ws-entregas`. Ejecuta desde la raíz del laboratorio: `./mvnw -q test`.

**Resultado esperado:** El test abre conexión WebSocket local al endpoint y finaliza en verde. El puerto lo asigna el sistema para evitar chocar con otro servicio.

**Fallo deliberado:** Cambia solo `/ws-entregas` del test por `/ws-equivocado`; ejecuta `./mvnw -q test`. **Diagnóstico:** La conexión falla porque no hay un endpoint registrado con ese nombre. Restaura la ruta.

**Entiende:** Un nombre de destino funciona como dirección postal: el mensaje debe llegar a la ruta que el servidor configuró. `/app` y `/topic` cumplen funciones diferentes.

**Cierra:** Anota qué ruta abre la conexión y qué prefijo leerías para ubicar un mensaje enviado al servidor.

#### Subtema 8.2: Suscríbete y recibe una posición · 10 min

**Contexto:** La conexión sola no recibe posiciones; el cliente se suscribe al envío que quiere observar.

**Hazlo tú:** Abre `src/test/java/academia/rutaflow/stomp/StompEndToEndTest.java`. Sigue `session.subscribe(...)`, el evento `PositionEvent` y `PositionPublisher.publish(...)`. El test confirma que el objeto publicado llega de vuelta por el WebSocket.

```java
session.subscribe("/topic/entregas/SHP-1", handler(PositionEvent.class, events));
PositionEvent first = new PositionEvent("SHP-1", 1, "2026-11-09T10:00:00Z", 1);
assertThat(publisher.publish(first)).isTrue();
assertThat(events.poll(3, TimeUnit.SECONDS)).isEqualTo(first);
```

Ejecuta `./mvnw -q test` desde `examples/spring-boot-stomp-rutaflow/`.

**Resultado esperado:** La prueba recibe `SHP-1` con secuencia `1`; no es una llamada directa al método del cliente, sino servidor, broker y cliente STOMP conectados.

**Fallo deliberado:** Cambia la suscripción a `/topic/entregas/SHP-2`. **Diagnóstico:** El test falla porque escucha el canal equivocado. El timeout limitado termina la espera y señala la falta de mensaje; no se cuelga indefinidamente. Restaura `SHP-1`.

**Entiende:** Publicador y suscriptor deben acordar el mismo destino. `PositionEvent` lleva ID, secuencia, hora y versión de esquema para que el receptor pueda interpretar y ordenar cambios.

**Cierra:** Copia del reporte de JUnit la línea que dice cuántas pruebas pasaron y nombra el destino exacto usado.

#### Subtema 8.3: Evita procesar dos veces la misma secuencia · 8 min

**Contexto:** Una conexión o productor puede repetir una actualización. Si ambos eventos se aplican, la app puede mostrar dos veces el mismo cambio.

**Hazlo tú:** Abre `src/main/java/academia/rutaflow/stomp/PositionSequenceTracker.java`. Identifica el último número guardado por envío. En `StompEndToEndTest.java`, localiza la segunda publicación del mismo `first`.

```java
assertThat(publisher.publish(first)).isTrue();
assertThat(publisher.publish(first)).isFalse();
assertThat(events.poll(3, TimeUnit.SECONDS)).isEqualTo(first);
assertThat(events.poll(250, TimeUnit.MILLISECONDS)).isNull();
```

Ejecuta `./mvnw -q test` y registra por qué la segunda llamada devuelve `false`.

**Resultado esperado:** Solo se recibe un evento. Para el mismo envío, una secuencia debe ser mayor que la última aceptada.

**Fallo deliberado:** En `PositionPublisher.publish`, quita temporalmente la condición que consulta `sequences.accept(event)` y publica siempre. **Diagnóstico:** Vuelve a ejecutar el test: la última comprobación falla porque llegó el duplicado. Restaura la condición y confirma el test verde.

**Entiende:** El tracker es una regla de orden, no una cola durable. Su mapa vive en memoria y una instancia; al reiniciar se borra y no coordina réplicas.

**Cierra:** Guarda reporte verde restaurado y el fallo que observaste al permitir publicar duplicados.

#### Subtema 8.4: Diagnostica destinos y límites de producción · 10 min

**Contexto:** El broker simple ayuda a aprender y probar el flujo, pero guarda sus suscripciones en memoria. La aplicación no valida aquí quién puede seguir un envío.

**Hazlo tú:** Ejecuta la prueba con el topic incorrecto y luego restáuralo. Abre `examples/spring-boot-stomp-rutaflow/README.md`; marca los límites sobre varias instancias, reinicios, autenticación y autorización por envío.

**Resultado esperado:** Puedes explicar por qué el suscriptor incorrecto no ve el mensaje, por qué el mapa de secuencias no basta en varias réplicas y qué permiso falta antes de exponer un envío real.

**Fallo deliberado:** Retira el timeout del `events.poll(...)` y observa que una prueba puede esperar para siempre cuando el destino no coincide. **Diagnóstico:** Restáuralo: las pruebas asíncronas necesitan un límite de espera.

**Entiende:** Para requisitos de confirmación STOMP, persistencia o múltiples instancias, evalúa un broker externo y su relay. Para clientes Socket.IO, hace falta un servidor compatible o gateway: compartir WebSocket como transporte no vuelve iguales los protocolos.

**Cierra:** Evidencia del tema: test verde restaurado, fallo diagnosticado del topic cambiado y respuesta breve sobre cómo proteger `/topic/entregas/{id}`.

**Transferencia al proyecto integrador:** aplica el flujo a una actualización de ruta: fija un contrato de evento, acuerda el destino con Flutter, y decide dónde guardar deduplicación y permisos. El ejemplo no implementa producción, ni integra Flutter o Keycloak.

**Cuándo no usarlo:** si basta con actualizar cada varios minutos, considera una consulta HTTP periódica sencilla. No mantengas conexiones persistentes sin una necesidad de tiempo real.

**Fuentes oficiales:** [Spring WebSocket y STOMP](https://docs.spring.io/spring-framework/reference/web/websocket/stomp.html), [broker simple: límites y alternativas](https://docs.spring.io/spring-framework/reference/web/websocket/stomp/handle-broker-relay.html).

### Tema 9: Archivos y notificaciones push · Avanzado · 40 min

**Objetivo observable:** aceptar una imagen decodificable de una lista permitida, guardar su contenido bajo una clave nueva y enviar un aviso solo tras el commit.

**¿Por qué es importante?** El nombre `foto.jpg` y el encabezado `Content-Type` los elige el cliente; por sí solos no demuestran qué bytes se recibieron. Y si se envía un push antes de confirmar la transacción, el teléfono podría anunciar una foto que luego no se guardó.

**Antes de empezar:** manejar un POST y reconocer una transacción del Módulo 17. Sigue el laboratorio `examples/spring-boot-upload-push-rutaflow/`; H2, el almacén de objetos y el gateway de push son de demostración, no servicios externos.

```mermaid
sequenceDiagram
  participant App as App cliente
  participant Api as API Spring
  participant Tx as Transacción
  participant Push as Listener y gateway de ejemplo
  App->>Api: POST foto multipart
  Api->>Api: Decodifica imagen y verifica límites
  Api->>Tx: Guarda bytes y metadatos
  Tx-->>Push: AFTER_COMMIT: entrega evento
  Push->>Push: Registra el aviso de prueba
```

```bash
cd examples/spring-boot-upload-push-rutaflow
./mvnw -q test
```

#### Subtema 9.1: Recibe el archivo con límites · 8 min

**Contexto:** Spring recibe el archivo multipart. El límite protege el servicio de cargas mayores al tamaño previsto; también se controla el alto y ancho de las imágenes.

**Hazlo tú:** Abre `src/main/resources/application.properties` y `UploadController.java`. Encuentra `max-file-size`, `max-request-size`, `app.upload.max-bytes` y el endpoint `POST /api/fotos`. Ejecuta el laboratorio:

```bash
./mvnw -q test
```

**Resultado esperado:** Las pruebas multipart arrancan en Spring local. Un archivo que supera el límite configurado recibe `415` del validador; el límite multipart del servidor es una barrera anterior, con su propio error HTTP.

**Fallo deliberado:** Sube el límite de bytes y comenta la comprobación `bytes.length > maxBytes` en `ImageContentValidator`. **Diagnóstico:** Ejecuta `archivoQueSuperaElLimiteConfiguradoSeRechaza`: deja de demostrar el rechazo. Restaura ambas líneas y corre la suite completa.

**Entiende:** Poner un límite es como definir el tamaño de una caja antes de abrirla. Un archivo pequeño también puede declarar dimensiones enormes, por eso se acota el total de píxeles antes de decodificar.

**Cierra:** Escribe los dos límites que verificaste: bytes del archivo e imagen decodificada.

#### Subtema 9.2: Comprueba el contenido de la imagen · 10 min

**Contexto:** Un MIME declarado correcto todavía puede esconder texto o una imagen truncada. La validación debe abrir y decodificar el contenido, no confiar solo en el sufijo o los primeros bytes.

**Hazlo tú:** Lee `ImageContentValidator.validate`. Observa que permite PNG/JPEG, obtiene dimensiones, compara el MIME declarado y lee la imagen. En `UploadPushIntegrationTest`, los PNG válidos se crean con `ImageIO`; el caso de firma parcial prueba que una cabecera no basta.

```java
if (reader.read(0) == null) throw new InvalidImageException("No se pudo decodificar la imagen");
```

**Resultado esperado:** Una imagen PNG completa pasa; texto renombrado `.jpg`, MIME falso y PNG truncado reciben `415` y no crean filas ni avisos.

**Fallo deliberado:** En el test `textoDisfrazadoComoJpegNoGuardaNiNotifica`, conserva el nombre `.jpg` y `image/jpeg`, pero reemplaza el contenido por texto válido. **Diagnóstico:** La respuesta debe seguir siendo `415`. ## Laboratorio práctico

**Objetivo del laboratorio:** comprobar el flujo completo del microservicio con JWT, autorización por rol, persistencia real, Actuator y una guardia de configuración.

**Requisitos previos:** Módulos 0-11 completados.

| Paso | Acción | Código | Explicación |
|---|---|---|---|
| 1 | Diseñar la arquitectura por capas completa | Ver Tema 1 | controller/service/repository/dto |
| 2 | Implementar persistencia con migraciones Flyway | Módulo 4 | Flyway aplica el esquema y Hibernate usa `ddl-auto=validate` |
| 3 | Proteger endpoints con Spring Security + JWT | Módulo 5 | Autorización por rol |
| 4 | Exponer Actuator con una métrica de negocio | Módulo 7 | Verifica en `/actuator/metrics` |
| 5 | Escribir tests de integración con Testcontainers | Módulo 6 | Cubriendo el flujo crítico completo |

**Verificación local:** desde `examples/spring-boot-integrador-rutaflow/`, ejecuta `./scripts/verify-integration.sh`. Las siete pruebas recorren PostgreSQL real, migración, HTTP, JWT, roles, métrica y guardia de configuración. Este resultado no certifica despliegue productivo; consulta `docs/salida-a-produccion.md` para los pendientes.

**Errores comunes y soluciones**

- **Dejar endpoints sensibles sin protección de autorización.** Verifica que cada endpoint tenga la anotación de autorización apropiada según su sensibilidad.
- **Confiar en `ddl-auto` en vez de migraciones versionadas para el proyecto final.** Usa Flyway consistentemente.
- **Omitir tests de integración del flujo crítico.** Prioriza cubrir con Testcontainers el camino principal completo de la aplicación.
